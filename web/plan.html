plan and method

Run a commit past several independent reviewers until they stop finding things

extracted from worker-pool #128 3 rounds · 2 agents · converged node 24 · zero runtime deps

A convergence loop: run independent review agents against a pushed commit, apply the findings that survive verification, push, and repeat until every agent reports nothing new. The loop is not the interesting part — the triage gate is. Roughly a third of what the reviewers suggested did not survive it.

One round

Everything below repeats per round. The round is genuinely ordered, so it is numbered.

  1. Pin a worktree at the pushed HEAD. Diff against git merge-base HEAD origin/master, never the trunk tip — see the traps below.
  2. Launch every enabled agent in parallel, in the background. The slowest agent sets the round's wall clock. Serialising a 20-minute agent behind a 2-minute one wastes most of it.
  3. Reproduce each finding against the real code — before touching anything. This is the step most easily skipped and the one carrying the value.
  4. Fix it, add a regression test, then reintroduce the bug and confirm the test fails. A test that passes both with and without the fix is decoration.
  5. Format, vet, run the full suite, amend, push --force-with-lease. Then append the newly-settled items to the prompt.
  6. Stop iff every agent emitted the stop token on the same commit. Otherwise round N+1.

Why it terminates instead of churning

  • A growing settled list. Without it, each fresh agent rediscovers the same deferred issues every round, forever.
  • A literal stop token. Termination is a grep, not a judgement call.

The prompt

prompts/review-round.md has four sections, in this order.

  1. What the change does. The design in a few bullets, so the agent does not have to infer intent.
  2. ALREADY SETTLED — do NOT re-report. A numbered list, appended to after every round. For deliberately deferred items, include the reasoning, so an agent can argue with the reasoning instead of re-proposing a fix you already rejected.
  3. What you want. The specific classes of defect. Always include the test-quality question:
  4. The stop token. Say exactly NO NEW FINDINGS on its own line.

“Would each assertion actually fail if the behaviour it guards regressed? Read the assertions, not the test names.”

That question produced every finding in rounds 2 and 3.

Plus DO NOT edit any files. You want findings to triage, not competing patches to merge.

prompts/feedback.md replies per finding as ACCEPTED / AGREE-BUT-DEFERRED / REJECTED, each with reasoning and each ending in a direct question. Closing the loop that way is what turned two “you should fix this” items into explicit agreement to defer them.

Operator errors the discipline caught

All near-misses that would otherwise have produced false confidence.

  • A simulated regression deleted the only use of an import, so the observed FAIL was a compile error, not a failing assertion. Re-run with the import kept in use — and the tests then passed, confirming the finding.
  • Two verification runs never executed: wrapped in timeout, which does not exist on macOS (exit 127). Empty output read as success.
  • A new deterministic test hung under regression instead of failing — the worker drained the buffered channel then blocked on an open, empty one. Closing the channel made it fail in 0.00s.
  • A mock rebuilt inside a loop silently stopped applying after the first iteration, so later iterations exercised the real implementation.

Triage rules that earned their place

  • Reproduce before fixing. Every accepted finding was demonstrated against the real code first.
  • Every fix gets a regression test, and the test gets verified by reintroducing the bug.
  • A test that hangs on regression is worse than one that fails. It burns the CI timeout and reads as an infra fault.
  • Distinguish “no hits” from “broken query”. When verifying against logs or metrics, run a control you know should return rows. A zero is not evidence until the pipe is proven.
  • An agent's suggested fix can be wrong even when its finding is right. Judge the two separately.

The reference run: #128

Change under review: replace a flat 30s retry wait after a failed CreateSandbox with exponential backoff (1s → 60s cap, jitter) in a prewarm-pool worker. Two agents, codex and droid, plus an in-platform reviewer that had already produced four rounds of findings before the loop started.

roundcommitcodexdroid
1bf94454no production issues; 1 low (test tautology)NO NEW FINDINGS

Zero production correctness findings across the three rounds — the production code had already been hardened by four earlier review rounds. Everything the loop found was tests asserting less than the PR claimed, all three the same species: a test that passes whether or not the behaviour exists.

  • Jitter was deletable with every test still green. Every assertion accepted the nominal delay as its upper bound, so return delay satisfied them. Fixed by asserting jitter shortens and varies across 200 draws.
  • The cancellation test was probabilistic. A regressed worker's select could still pick ctx.Done() first in all 20 runs — a ~1-in-10⁶ false pass. Made deterministic by stubbing the wait while leaving the context live.
  • The tests validated their own constants. Expected bounds were derived from the constants under test, so changing the cap to 48s left every test green while breaking the documented contract. Fixed by pinning the literal values in a separate test.

Cost

codex ~15–20 min per round, droid ~2 min, run in parallel → ~20 min per round wall clock. Three rounds plus one feedback exchange ≈ 1.5 h of agent time. Yield: 3 real test defects, 5 rejected suggestions, 4 operator errors surfaced.

Agents are configuration

The loop is agent-agnostic; codex and droid are just the two entries that happen to be enabled. Adding a third is a config change, not a code change. Only three things actually vary between agents, and all three bit during the reference run.

A verbose agent's stdout is a full transcript that contains the prompt, so grepping the whole stream for the stop token matches the instruction that asked for the token. Parse the final report block — hence parse.reportFrom.

Why a CLI and a skill, not one of them

Reviewers and the main agent reach the system in completely different ways, and that difference decides the design. Reviewers need no cooperation — they are subprocesses; whatever spawns them already owns their stdout, exit code, wall time and round. Their output is the data. The main agent has to report — it is not a subprocess of anything, and its most valuable output is a judgement (this reproduces, that one does not, this fix leaks a reservation) that nothing captures unless it is deliberately emitted.

A binary cannot make those judgements. Instructions cannot capture a subprocess. Hence two pieces.

Hard rule: the CLI must work without the skill. If macr review only functions inside a session reading SKILL.md, it is not a tool — it is a prompt with a binary attached, and it cannot run in CI or for anyone on a different agent.

The event log

One append-only NDJSON file per PR: runs/<id>/events.ndjson. Two writers are safe — the CLI appends agent events while the main agent appends verdicts.

{"t":"round.start","n":2,"sha":"6901882"}
{"t":"agent.launch","agent":"codex","round":2}
{"t":"agent.report","agent":"codex","round":2,"verdict":"found","raw":"…"}
{"t":"finding.raised","id":"X1","agent":"codex","claim":"jitter is deletable","file":"main_test.go:2237"}
{"t":"finding.reproduced","id":"X1","evidence":"return delay → all backoff tests PASS"}
{"t":"finding.resolved","id":"X1","verdict":"accepted","reason":"now asserts jitter varies"}
{"t":"commit.pushed","sha":"ae473ab"}
{"t":"round.end","n":2}

The console folds the log into the current view, and three things fall out for free: the timeline is measured rather than estimated, a run can be replayed, and the view is derived state rather than a hand-written report.

Enforce the half that is checkable

Today the triage gate holds only because the operator chose to be disciplined. A skill can be skipped; a check cannot. Enforce the mechanical half — an accepted finding must have a recorded reproduction, a fix must have a test that was observed failing without it — and leave the judgement half to the skill.

macr finding resolve X1 --verdict accepted
  → refused: no finding.reproduced event for X1

Where this actually is

The proof of concept does not build the orchestrator. The main agent drives the loop by hand, as it did for #128, and writes the run file the console reads. That keeps the POC to the question worth answering — is a second PR's review useful? — rather than spending the time on process supervision.

commandstate
macr review [flags]runs one round: every reviewer reads the diff, findings are recorded. Iterating to convergence is still manual. --dry-run exercises the pipeline without spawning anything.

Still to build

  • An agent registry: invocation, cwd handling, whether sessions resume, expected latency.
  • Prompt assembly: template plus the accumulated settled list, versioned per round.
  • A findings model — {id, agent, round, severity, file, line, claim, status} with status one of accepted | deferred | rejected | superseded — so the settled list generates itself.
  • The reproduce/fix/verify gate as an explicit state machine.
  • Convergence detection across N agents on a single commit sha.
  • A per-round budget, because the long-tail agent dominates wall clock.
Deliberately not automated: applying a fix without first reproducing the finding. That gate is where the value was.

Known traps

  • Diff base. git diff origin/master shows commits master gained since your branch point as deletions in your diff. Always diff against git merge-base HEAD origin/master. This produced a confident, completely spurious finding on round zero.
  • Prompt-induced findings are your bug, not theirs. Fix the prompt and say so.
  • timeout does not exist on macOS. Wrapping a verification in it exits 127 and the command never runs — an empty result that looks like a pass.
  • Removing a call can orphan an import, turning “the test caught it” into a compile error. Keep the import used when simulating a regression.
  • Mock frameworks may not re-apply inside a loop. Build the mock once outside; re-building per iteration silently kept the real implementation (mockey).
  • Agents recycle suggestions when they have nothing left. A verbatim repeat of a prior cosmetic note is a decent signal of convergence.
