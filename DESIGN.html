Anatomy of a Round

Three reviewers read the same commit and never see each other. What happens between their reports and the next round — the barrier, the serial triage, and the four conditions that let the loop stop.

The shape

Concurrent, then serial, then concurrent

A round has three movements, and they do not share a rhythm. Reviewers run all at once. Triage runs strictly one finding at a time. Replies go out all at once again. The two barriers between them are ordinary await Promise.all calls, and almost everything surprising about the loop's behaviour falls out of where they sit.

Ordering

Triage is per finding. Replies are per agent.

These are easy to conflate, and they behave differently. Triage never talks to a reviewer at all — the main agent is reading code and reproducing bugs alone. The conversation happens later, in the reply step.

Triage · serial

Ordered by the event log, not by agent.

findingsIn() replays finding.raised events into a Map; outstanding() iterates its values, so insertion order wins. Findings appear agent-clustered only because codex finished first — had grok reported first, grok's would be judged first.

Reply · concurrent

One thread each, scoped to its own findings.

threadFor(agent, findings) filters to that reviewer's items. Another reviewer's name and finding ids are stripped by scrub() before sending — isolation enforced in code, not trusted to whoever wrote the verdict text.

Independence is the whole reason for running more than one reviewer. Two that read each other stop being independent, and their agreement stops counting as evidence — so a verdict saying "grok raised this too" would quietly destroy the thing being measured.

Why serial

The bottleneck is deliberate

Judging findings concurrently would put several agents in one worktree at once, and the second fix would land on top of the first without having seen it. Correct, but it makes a round with twenty findings long — the first entry in TODO.md, and still open. 

// bin/jury.js — the triage loop, one finding at a time
for (const f of todo) {
  if (deadlocked(events, f.id)) // 3 turns per claim → defer, never accept
    continue;

  const heart = beat(dir, main.name, round, f.agent); // tagged: whose thread
  const v = await triageOne(main, f, { worktree, trunk });

  // reproduction recorded BEFORE the verdict — gate() reads the folded log,
  // so an acceptance is checked against disk, not against what we know here
  if (v.reproduced) await appendEvent(dir, { t: "finding.reproduced", … });
  findings = await findingsIn(dir);  // refold, THEN record
  const res = await record(dir, findings, f.id, v);
  if (!res.ok) continue;  // the gate refusing is the gate working
}

That refold ordering is not incidental. The map is folded before the reproduction is appended, so recording first meant every accepted finding was refused for having no reproduction, moments after one had been written for it.

The gate

What a verdict has to survive

A skill can be skipped; this check cannot. The mechanical half of triage discipline is enforced in lib/findings.js, and a refusal downgrades the finding back to open rather than crashing the run.

rejected
Passes freely. Say what you checked and why the claim is wrong.
deferred
Real, pre-existing, out of scope — and you changed nothing. If you edited a file, this is the wrong verdict.
accepted
needsa recorded reproduction — no finding.reproduced event, no acceptance.
needsproof the test failed without the fix — a test that passes either way is decoration.
no verdict
left openDeliberately not silent. An unjudged finding must be raised again rather than vanishing into a round that reports convergence.

Deferring is not agreeing

After three turns on one claim the main agent stops arguing and defers — both positions are already in the log. Defer, never accept: fixing something nobody demonstrated is how a stubborn false positive gets code written for it, and it would require bypassing the gate to do it.

Stopping

Convergence is four conditions

Every one is required, and the third is the one that was missing at first. A round that raised findings nobody triaged used to report success: every thread had nothing to answer, and nothing to answer counted as clean.

1answers.every(a => a.clean) — every reviewer signed offheld
2!broke.length — no reviewer failed to runagy · quota
3!stillOpen.length — nothing left open from any earlier roundheld
4!pushFailed — the fixes actually reached the branchheld
→ one condition fails ⇒ round N+1, up to --rounds (default 10)

Consequence

A blocked reviewer caps every run at max rounds.

agy's quota error is failed, not clean, so condition 2 can never hold while it is enrolled. The run burns all ten rounds and never converges. That is the design working — a reviewer that cannot run is not evidence of agreement — but drop it from --agents until the quota resets.

Consequence

One wedged reviewer stalls the whole round.

The barrier joins on the slowest. In the measured run codex sat idle for four minutes waiting on grok before triage could begin. Bounded only by each agent's own timeout — --print-timeout 20m for agy.

Between rounds

The settled list, refreshed first

refreshSettled(dir) runs before the round, not after. buildPrompt reads settled.md, so a list written afterwards would take effect one round too late, and the next reviewer would re-raise something already decided.

It is regenerated from the log rather than hand-maintained, which is what makes the loop terminate at all: without it, every fresh reviewer rediscovers the same deferred issues, round after round, forever.

One known gap

A rejected finding can still be re-raised once by the next reviewer, because it only reaches the settled list after the round it was rejected in. The turn limit bounds the argument; it does not prevent the first repeat.

Underneath

Everything is a fold over one file

There is no stored state to drift. runs/<id>/events.ndjson is append-only, two writers are safe, and every view — the findings map, the conversation threads, the timeline, convergence itself — is derived by replaying it.
